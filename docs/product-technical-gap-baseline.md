## Product responsibility

The Learning Record Store is the authoritative persistence boundary for xAPI statements, xAPI document resources, attachments, and their integrity/provenance evidence. It does not own enrollment, completion policy, authored content, psychometric responses, billing state, or downstream product workflow truth.

## Feature specification

The first executable feature is immutable tenant-scoped Statement ingestion. `statement_validation` supplies received-version-aware comparison bytes; `StatementKernel` proves the pure domain decision for first acceptance, exact replay, conflict, and atomically rejected batches at `(tenant_key, statement_key)`. `persist_statement_occurrence` implements the controlled single-item PostgreSQL transaction primitive, while migration 0004 adds the proposed `persist_statement_batch` primitive for a fully validated POST array: one immutable request receipt, one indexed occurrence per submitted item, and all-or-none canonical mutation. Every durable attempt retains exact request evidence once the persistence primitive is entered, compatibility-version changes cannot silently mutate canonical evidence, every stored conflict in a rejected batch is classified as `conflict`, and voiding is relational rather than destructive.

`migrations/0001_statement_evidence.sql` establishes the 3NF evidence schema and rejects identifiers or version labels composed entirely of PostgreSQL whitespace so durable validation matches the Rust kernel's fail-closed blank-identity contract. It also makes the two immutable SHA-256 claims database invariants: `ingestion_receipt.request_content_hash` must equal SHA-256 over `raw_request_bytes`, and `statement_record.content_hash` must equal SHA-256 over `comparison_bytes`. Migration 0002 binds forced RLS to an administrator-controlled `tenant_database_principal` mapping keyed by PostgreSQL `session_user`, moves controlled writes behind a constrained `SECURITY DEFINER` owner, removes caller-selected `app.tenant_key` as an authorization source, and applies the same whitespace-only rejection at the controlled function boundary. Migration 0003 adds explicit `batch_rejected` persistence and requires every `accepted`/`replayed` occurrence to carry the canonical submitted Statement key. Migration 0004 adds the proposed one-receipt/many-item transaction and gives controlled single-item and batch writers one per-Statement transaction-serialization protocol. ADR 0002 and ADR 0003 remain Proposed until exact-head integration evidence and ordinary protected-branch acceptance exist.

## DDD/context map

**Core subdomain:** Learning Record Evidence. **Supporting:** Protocol Compatibility, Document Resources, Attachment Evidence, Tenant Authorization, and Conformance Evidence. **Generic:** PostgreSQL durability, object storage, telemetry, deployment, and recovery.

The Learning Record Evidence bounded context uses `StatementCandidate`, `StoredStatement`, `IngestionReceipt`, `StatementOccurrence`, and `VoidingRelation`. `StatementKernel` is the pure domain service. `persist_statement_occurrence` and proposed `persist_statement_batch` are internal durable repository primitives; a Rust `StatementEvidenceRepository` will be the application-facing repository boundary and must delegate rather than duplicate accepted/replayed/conflict decisions. A rejected batch is a request-level invariant: no candidate becomes canonical, every submitted index remains attributable to the shared receipt once the validated batch enters persistence, and every candidate that conflicts with stored canonical evidence remains classified as a conflict. Canonical Statement plus immutable ingest/voiding facts form the minimum consistency boundary; no tenant-wide lock is permitted.

Tenant Authorization is a supporting bounded context and an anti-corruption boundary around database identity. `tenant_database_principal` is an administrator-owned mapping, not a customer-editable domain record. Data-plane callers cannot select tenant scope by supplying a GUC or arbitrary tenant identifier. Potential domain events (`StatementAccepted`, `StatementReplayed`, `StatementConflictObserved`, `StatementVoided`) are emitted only after durable commit when a real consumer exists.

Learning Management Platform consumes released learning evidence for progression/completion policy. `learning-interoperability-contracts` owns reusable cross-product interoperability definitions. Compatibility adapters are an anti-corruption layer and never become a shared kernel of canonical learning truth. Cross-repository database reads are forbidden.

## Persistence and transaction invariants

Relational authoritative facts remain in 3NF. Named persistence objects use at least two semantic words and `snake_case`. Every tenant-owned reference carries `tenant_key`. Raw evidence is stored as bytes, not normalized JSON. Text identity/version constraints reject strings composed only of PostgreSQL whitespace, matching the Rust kernel's Unicode-whitespace blank rejection for the currently exercised tab/newline cases. Immutable digest columns are not caller-trusted assertions: `request_content_hash = sha256(raw_request_bytes)` and `content_hash = sha256(comparison_bytes)` are schema constraints as well as controlled-writer behavior. Successful `statement_ingestion_item` rows require a non-null resolved key equal to the submitted key; conflict and `batch_rejected` rows require no resolved canonical key. Canonical Statement rows are immutable and ordinary data-plane principals do not receive direct evidence-table mutation privileges.

The controlled item-level and batch primitives use the same transaction-scoped per-Statement advisory-lock protocol. A single-item write locks its `(tenant_key, statement_key)` identity before durable comparison/mutation. A batch validates its shape and duplicate identities, acquires distinct identities in lexical order, writes one request receipt, re-reads canonical state under those locks, and either inserts all missing canonical Statements when the complete batch is conflict-free or inserts none when any stored conflict is found. Hash collisions may conservatively serialize unrelated identities but cannot authorize or manufacture a conflicting canonical write; the primary key, RLS, immutable digest constraints and occurrence consistency checks remain final database invariants. Lock-wait telemetry and realistic hot-key measurement are required before any partition/read-write-split decision.

A validated POST-array adapter must materialize the bounded collection before invoking the durable batch primitive. Calling the single-item primitive independently for every array member remains forbidden because it would violate shared request provenance and atomicity. Duplicate identity, malformed shape and request-context failures currently fail before migration 0004 creates a receipt, so the future Rust repository/network adapter must preserve those request-level failures as immutable evidence without turning them into canonical Statements. The public Rust boundary rejects receipt issuance once the next value would exceed PostgreSQL signed `bigint`, rejects direct occurrence indexes above signed `integer`, and rejects batch cardinality whose zero-based indexes cannot be represented by that durable `integer` contract.

## Security evidence and research traceability

Proposed ADR 0002 records the authorization design. PostgreSQL documents `session_user` as the connection-establishing principal while `current_user` changes under `SECURITY DEFINER`; forced RLS applies policy expressions to row visibility and writes. OWASP authorization guidance supports least privilege, deny-by-default behavior, per-request authorization checks, and dedicated authorization tests. The repository test contract therefore treats custom GUCs as non-authoritative, keeps migration/admin credentials separate from data-plane identities, and proves both privilege and tenant-isolation failure paths.

Proposed ADR 0003 records the shared batch transaction decision, its rejected coarse-lock/SERIALIZABLE-only alternatives, deterministic identity ordering, user/failure scenes and follow-up lock-wait evidence. Neither ADR becomes Accepted merely because its source exists on this PR; exact-head execution/review and ordinary integration remain mandatory.
