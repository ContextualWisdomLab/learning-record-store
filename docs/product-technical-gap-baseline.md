## Product responsibility

The Learning Record Store is the authoritative persistence boundary for xAPI statements, xAPI document resources, attachments, and their integrity/provenance evidence. It does not own enrollment, completion policy, authored content, psychometric responses, billing state, or downstream product workflow truth.

## Feature specification

The first executable feature is immutable tenant-scoped Statement ingestion. `statement_validation` supplies received-version-aware comparison bytes; `StatementKernel` proves the pure domain decision for first acceptance, exact replay, conflict, and atomically rejected batches at `(tenant_key, statement_key)`; `persist_statement_occurrence` implements the current single-item durable PostgreSQL transaction primitive. Every attempt retains exact request evidence, compatibility-version changes cannot silently mutate canonical evidence, every stored conflict in a rejected batch is classified as `conflict`, and voiding is relational rather than destructive.

`migrations/0001_statement_evidence.sql` establishes the 3NF evidence schema and now rejects identifiers or version labels composed entirely of PostgreSQL whitespace so durable validation matches the Rust kernel's fail-closed blank-identity contract. It also makes the two immutable SHA-256 claims database invariants: `ingestion_receipt.request_content_hash` must equal SHA-256 over `raw_request_bytes`, and `statement_record.content_hash` must equal SHA-256 over `comparison_bytes`. Migration 0002 closes the bootstrap authorization gap by binding forced RLS to an administrator-controlled `tenant_database_principal` mapping keyed by PostgreSQL `session_user`, moving controlled writes behind a constrained `SECURITY DEFINER` owner, removing caller-selected `app.tenant_key` as an authorization source, and applying the same whitespace-only rejection at the controlled function boundary. Migration 0003 adds the explicit `batch_rejected` persistence outcome and now requires every `accepted`/`replayed` occurrence to carry the canonical submitted Statement key, so PostgreSQL three-valued CHECK semantics cannot admit a null successful resolution. A Rust repository/network adapter and a durable one-receipt/many-item transaction remain unfinished.

## DDD/context map

**Core subdomain:** Learning Record Evidence. **Supporting:** Protocol Compatibility, Document Resources, Attachment Evidence, Tenant Authorization, and Conformance Evidence. **Generic:** PostgreSQL durability, object storage, telemetry, deployment, and recovery.

The Learning Record Evidence bounded context uses `StatementCandidate`, `StoredStatement`, `IngestionReceipt`, `StatementOccurrence`, and `VoidingRelation`. `StatementKernel` is the pure domain service. `persist_statement_occurrence` is the current durable single-item repository primitive; a Rust `StatementEvidenceRepository` will be the application-facing repository boundary and must delegate rather than duplicate accepted/replayed/conflict decisions. A rejected batch is a request-level invariant: no candidate becomes canonical, but every submitted index remains attributable to the shared receipt and every candidate that conflicts with stored canonical evidence remains classified as a conflict. Canonical Statement plus immutable ingest/voiding facts form the minimum consistency boundary; no tenant-wide lock is permitted.

Tenant Authorization is a supporting bounded context and an anti-corruption boundary around database identity. `tenant_database_principal` is an administrator-owned mapping, not a customer-editable domain record. Data-plane callers cannot select tenant scope by supplying a GUC or arbitrary tenant identifier. Potential domain events (`StatementAccepted`, `StatementReplayed`, `StatementConflictObserved`, `StatementVoided`) are emitted only after durable commit when a real consumer exists.

Learning Management Platform consumes released learning evidence for progression/completion policy. `learning-interoperability-contracts` owns reusable cross-product interoperability definitions. Compatibility adapters are an anti-corruption layer and never become a shared kernel of canonical learning truth. Cross-repository database reads are forbidden.

## Persistence and transaction invariants

Relational authoritative facts remain in 3NF. Named persistence objects use at least two semantic words and `snake_case`. Every tenant-owned reference carries `tenant_key`. Raw evidence is stored as bytes, not normalized JSON. Text identity/version constraints reject strings composed only of PostgreSQL whitespace, matching the Rust kernel's Unicode-whitespace blank rejection for the currently exercised tab/newline cases. Immutable digest columns are not caller-trusted assertions: `request_content_hash = sha256(raw_request_bytes)` and `content_hash = sha256(comparison_bytes)` are schema constraints as well as controlled-writer behavior. Successful `statement_ingestion_item` rows require a non-null resolved key equal to the submitted key; conflict and `batch_rejected` rows require no resolved canonical key. The item-level UPSERT contract is executable: authorize tenant from the authenticated database principal; persist request evidence; serialize only the target `(tenant_key, statement_key)` identity through the primary-key conflict path; insert once or compare received version/comparison algorithm/digest/comparison bytes; persist `accepted`, `replayed`, or `conflict`; and return the outcome without throwing a domain-conflict exception that would roll back its receipt. Canonical Statement rows are immutable and ordinary data-plane principals do not receive direct evidence-table mutation privileges.

`persist_statement_occurrence` is deliberately item-level. A validated POST-array adapter must create one request receipt and associate multiple zero-based `statement_ingestion_item` rows to it. Request-level duplicate/context/conflict rejection must preserve an occurrence for every submitted index; non-conflicting siblings use `batch_rejected`, while every item conflicting with stored canonical evidence uses `conflict`. Calling the single-item primitive independently for every array member would violate request provenance and atomicity. The public Rust boundary rejects receipt issuance once the next value would exceed PostgreSQL signed `bigint`, rejects direct occurrence indexes above signed `integer`, and rejects batch cardinality whose zero-based indexes cannot be represented by that same durable `integer` contract. `ingest_batch` intentionally requires an exact-size validated candidate collection because the domain invariant requires complete request preflight before canonical mutation; network/streaming adapters must finish validation and materialize the bounded collection before invoking the kernel. Hot-key lock waits and contention must be measured before partitioning or read/write separation. No heuristic sharding or weighting is introduced without measured evidence.

## Security evidence and research traceability

ADR 0002 records the authorization repair. PostgreSQL documents `session_user` as the connection-establishing principal while `current_user` changes under `SECURITY DEFINER`; forced RLS applies policy expressions to row visibility and writes. OWASP authorization guidance supports least privilege, deny-by-default behavior, per-request authorization checks, and dedicated authorization tests. The repository test contract therefore treats custom GUCs as non-authoritative, keeps migration/admin credentials separate from data-plane identities, and proves both privilege and tenant-isolation failure paths.
